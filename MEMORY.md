## 2026-08-01 (later), Technical pipeline made per-item for multi-item projects
**What was decided:** Evans clarified the real business rule with the Grejoy project (2 items: a Trialco sliding window + a Trialco sliding door under one client project): a "project" is a client job that can contain several distinct items (different profiles/products, e.g. a big house needing a window AND a door). A new item means a genuinely new profile requiring its own material take-off — quantity of the SAME item is handled by qty on that one item, not by adding a new item. Extraction (material generation) must happen **one item at a time**, independently, throughout the whole technical pipeline (extraction → drawing → factory release), and Evans confirmed this scoping applies the same way through every stage, not just extraction. The commercial side is the one place items reconverge: all of a project's approved item extractions combine into **one client-facing quote**.
**Why:** Found while debugging a real report — after adding a 2nd item (door) to the Grejoy project, the Technical Workflow screen still only reflected the first item. Root cause: `TechnicalExtraction`/`DrawingTask`/`ProductionRelease` are all scoped to `project_id` only (no `design_id`/item link at all — see models.py), and `generate_extraction_from_design` silently grabs whichever item was saved most recently in the project. The system was never built to hold two independent extraction/drawing chains under one project; it assumed one project == one item's worth of technical work.
**What was rejected:** Treating this as a UI-only bug (it isn't — there's no column linking extraction/drawing/release records to a specific item, so nothing to display even if the UI looped over items); keeping extraction/quote/drawing all merged at project level with a "which item is this row for" free-text label instead of a real FK (would keep the same silent-overwrite risk documented in the 2026-07-29 revision-integrity decision).
**Plan:** See `docs/CHECKLIST.md` §E for the full build checklist (schema, endpoints, both frontend pages, tests). Schema change is additive-only via the existing SQLite auto-migrate pattern (`_auto_migrate()` in main.py) — will back up `backend/sofaamy.db` first and get explicit confirmation before restarting the backend against the real dev database, per the Hard Stops rule on schema changes.
**Discovered mid-build:** The live app is not on local SQLite — `backend/.env` points `SOFAAMY_DATABASE_URL` at a real Supabase Postgres database (that's where Grejoy's actual data lives). `_auto_migrate()` explicitly skipped Postgres entirely, and `create_all` never adds columns to tables that already exist in any dialect — so the new `design_id`/`extra_extraction_ids` columns would not have appeared there on their own. Evans chose (2026-08-01, in-session): extend auto-migrate for Postgres too, via a new `_auto_migrate_postgres()` branch using `ADD COLUMN IF NOT EXISTS` — applies automatically the next time the backend starts against Supabase, no manual step. The Supabase database itself was not touched in this session.
**Built:** `design_id` (nullable) added to `TechnicalExtraction`/`DrawingTask`/`ProductionRelease`; `extra_extraction_ids` (JSON text, matching the existing `file_manifest` convention) added to `Quote` so one quote can bundle several items. Revision numbering and all "current chain" superseding scoped to `(project_id, design_id)` — `None` groups every pre-existing record exactly as before, so every existing single-item project is unaffected. New `POST /api/projects/{id}/extractions/assign-to-item` lets a technical person explicitly hand a project's pre-existing ungrouped chain to one real item — never auto-guessed. `_technical_workflow_payload` gained `items[]`/`item_summary{}`; every extraction/drawing-task/release row now carries its own `design_id`. Frontend: Technical Workflow shows an item-picker tab row (only when a project actually has >1 item) scoping the Extraction/Drawing tabs; Quotations shows a checklist of every item with an approved extraction and combines the checked ones into one quote/snapshot/quote number.
**Bugs caught while writing tests (fixed before reporting done):** (1) a "bundled extraction is for the same item as the primary" validation branch was dead code — impossible to trigger, since approving an item's new extraction always supersedes that item's previous approved one — removed rather than left as unreachable defensive code. (2) Quotation `basis_status`/`requires_review` and drawing-task `basis_status` were still comparing against the single project-wide "approved extraction" — every real item's drawing task would have shown as permanently stale once items had their own chains. Fixed with a per-design_id cache (`_chain_ids_for`) so each quote/task compares against its own item's current chain.
**Verified:** 15/15 backend tests pass (7 pre-existing + 8 new). Full browser walkthrough (Playwright, local throwaway SQLite, real Supabase untouched) on a project shaped exactly like Grejoy (window + door): independent per-item extraction chains confirmed (saving one item's extraction left the other's untouched, both directions), both approved, then combined into one client quote (E1 + E1, ₵4,800, correct tax math) from the Quotations page — zero console/page errors. Frontend production build clean.
**What was rejected:** Guessing which item a project's pre-existing ungrouped extraction belongs to (explicit human assignment instead); a `quote_extractions` join table (the simpler additive JSON column matches this codebase's existing `file_manifest` pattern); making per-item selection mandatory even for single-item projects (would add clicks to the common case for zero benefit).
**Not done in this session:** Confirming against the actual live Grejoy project on Supabase (needs the next backend deploy/restart to pick up the Postgres migration — intentionally not triggered here); reports-page (`/api/reports/{kind}`) per-item accuracy for multi-item projects (flagged as a known gap in `docs/CHECKLIST.md` §E, not required for the reported bug); a true multi-item rollup for the top-level `ChainIntegrity` banner (cosmetic only — each item's real status is correct and visible via the item picker).

## 2026-09-16, Serverless startup DDL serialized behind a Postgres advisory lock to stop cold-start deadlocks
**What was decided:** Every Vercel cold start ran `Base.metadata.create_all` + 10 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` + `ensure_engine_materials` at import time against the shared Supabase Postgres. With several instances cold-starting at once, concurrent DDL deadlocked (`AccessExclusiveLock` vs `AccessShareLock` — `pent&crashed the whole instance, 500ing every request during that window (`could not import app/main.py`), which is what made the dashboard hang and produced the `psycopg2.errors.DeadlockDetected` / `SSL connection has been closed` / `terminating connection due to administrator command` stack in Vercel logs. Fix: a new `_startup_init()` runs the entire Postgres bootstrap (create_all + `_auto_migrate_postgres(conn)` + `ensure_engine_materials(Session(bind=conn))`) inside one `engine.begin()` transaction guarded by `SELECT pg_advisory_xact_lock(72991)` — the first instance does the work, the rest wait and then no-op via IF NOT EXISTS guards. Advisory xact lock auto-releases on commit or connection death (safe under Supabase's PgBouncer transaction pooler). SQLite path unchanged. `_auto_migrate_postgres` now takes the connection as its only argument.
**Why:** Schema in the cloud was already complete (verified all wanted columns present after the data export), so the DDL was pure per-boot waste whose only effect was the deadlock. Advisory-lock serialization is the minimal change that removes the deadlock without dropping the create_all/migrate safety net for genuinely new columns on first deploy.
**What was rejected:** Removing create_all/migrations from startup entirely (loses first-deploy auto-schema, and an empty cloud DB would need a manual step); a dedicated migration tool (Alembic) — bigger change than the bug warrants right now; session-scoped `pg_advisory_lock` instead of xact lock (leaks/violates semantics under transaction pooling).
**Verified:** 42 backend tests pass; `import app.main` clean against both SQLite (throwaway /tmp db) and live Supabase (advisory-locked init, all DDL no-ops since columns exist).
**Follow-up needed:** Redeploy to Vercel for the fix to take effect. Consider later: move schema management off boot-time entirely (Alembic) once the product stabilizes. The Configurator's hardcoded "127.0.0.1:8000" on API failure message is still client-visible and unguarded.
